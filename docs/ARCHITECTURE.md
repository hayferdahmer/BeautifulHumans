# Архитектура Beautiful Humans

**Версия:** 0.1.0  
**Статус:** фундамент Stage 1  
**Целевая сборка:** Project Zomboid 42.21.0

---

## 1. Цели архитектуры

1. Единая платформа, а не набор несвязанных модов.
2. Направленные зависимости и отсутствие циклов.
3. Базовая игра — источник истины для здоровья, крови и заражения.
4. Данные отделены от правил, интеграции и представления.
5. Один сбой не должен ломать независимые подсистемы.
6. Сохранения версионируются и мигрируют.
7. Критические сетевые изменения подтверждаются сервером.

## 2. Границы v0.1

В v0.1 реализованы:

- BH Core;
- BH Persistence;
- BH Anatomy;
- BH Physiology;
- BH Medical;
- BH Integration (события и наблюдение игрока);
- внутренняя шина событий;
- консольные команды разработчика;
- тестовый мод.

Не реализованы:

- BH Undead (кроме пассивного моста);
- BH Equipment;
- BH Engineering;
- BH World;
- BH Wildlife;
- BH Society;
- BH Civilization;
- BH Tactical;
- полноценный UI;
- сетевая авторизация лечения.

## 3. Слои

Каждая подсистема разделяется на четыре уровня:

| Уровень | Ответственность | Пример |
|---|---|---|
| Модель | какие данные существуют | `Injury`, `CharacterExtension` |
| Правила | как данные меняются | `Anatomy.Rules`, `Medical.CanApply` |
| Интеграция | связь с событиями и API игры | `PlayerObserver` |
| Представление | интерфейс, звук, анимация | отложено |

Правило: **UI и интеграция не вычисляют медицинские показатели напрямую**.
Они вызывают публичные методы правил.

## 4. Компоненты

### 4.1. Core

Файл: `src/shared/BH/Core.lua`.

Отвечает за:

- версию и API-версию;
- пространство имён `BH`;
- конфигурацию;
- журнал;
- шину событий;
- реестр модулей;
- разрешение зависимостей;
- запуск модулей;
- диагностический снимок.

Core **не содержит** медицинских, экономических или боевых правил.

### 4.2. Persistence

Файлы:

- `src/shared/BH/Persistence/Schema.lua`;
- `src/shared/BH/Persistence/Persistence.lua`.

Отвечает за:

- создание character extension;
- чтение/запись `player:getModData().BH`;
- проверку схемы;
- миграции;
- ремонт повреждённых записей;
- карантин;
- ограничение объёма.

### 4.3. Anatomy

Файлы:

- `Zones.lua` — 17 зон и отображение на `BodyPartType`;
- `Rules.lua` — чистые формулы тяжести и функциональных ограничений;
- `Model.lua` — жизненный цикл травм.

### 4.4. Physiology

Файл: `Physiology.lua`.

Выводит боль, кровопотерю и функциональную способность из травм. Не создаёт
параллельные шкалы голода/жажды/сна.

### 4.5. Medical

Файлы:

- `Treatments.lua` — каталог действий;
- `Medical.lua` — проверки, эффекты, идемпотентность.

### 4.6. Integration

Файлы:

- `GameEvents.lua` — регистрация событий PZ;
- `PlayerObserver.lua` — наблюдение `BodyDamage`;
- `Commands.lua` — отладочные команды.

## 5. Граф зависимостей

```text
bh.core
├── bh.persistence
│   └── bh.anatomy
│       ├── bh.physiology
│       │   └── bh.medical
│       └── bh.integration
└── bh.testmod (внешний тестовый мод)
```

Зависимости только направленные. `bh.integration` зависит от медицинского
модуля, но медицинский модуль не зависит от интеграции.

## 6. Загрузка

### 6.1. Структура мода Build 42

```text
BeautifulHumansCore/
├── mod.info
├── common/
│   ├── mod.info
│   └── media/
└── 42/
    ├── mod.info
    └── media/
        └── lua/
            ├── shared/
            ├── client/
            └── server/
```

Build 42 сканирует `common/mod.info` и `<version>/mod.info`. Корневой
`mod.info` оставлен для совместимости, но недостаточен.

### 6.2. Последовательность

1. Игра загружает Lua-файлы мода.
2. `BH_Bootstrap.lua` подключает Core и модули.
3. Модули вызывают `BH.RegisterModule(...)`, но не выполняют тяжёлую работу.
4. `BH.Boot()` регистрирует события PZ.
5. `OnGameStart` (одиночная игра) или `OnServerStarted` (сервер) вызывает
   `BH.Start()`.
6. `BH.Start()` разрешает зависимости и инициализирует модули.
7. `OnCreatePlayer` создаёт/читает character extension.
8. `OnPlayerUpdate` с частотой `tickInterval` наблюдает базовое состояние.

`BH.Start()` идемпотентен: повторный вызов возвращает прежний результат.

## 7. Шина событий

### 7.1. Формат

```lua
BH.Events.Emit("Character.InjuryCreated", {
    characterKey = "player:1",
    zone = "left_thigh",
    injury = { id = "left_thigh-000001", kind = "cut", severity = 40 },
})
```

### 7.2. Правила

- имена: `^[A-Za-z0-9_%.%-]+$`;
- порядок: приоритет по убыванию, затем порядок регистрации;
- ошибка одного обработчика не останавливает остальные;
- повторный вход в то же событие блокируется;
- глубина вложенности ограничена;
- бюджет доставки ограничен;
- payload — только простые данные, без живых игровых объектов.

### 7.3. Базовые имена

```text
Core.Booted
Core.Started
Core.ModuleFailed

Character.InjuryCreated
Character.InjuryHealed
Character.BleedingChanged
Character.TreatmentApplied
Character.PhysiologyChanged

Zombie.FunctionChanged
Item.ConditionChanged
```

## 8. Идентификаторы

| Сущность | Формат | Пример |
|---|---|---|
| Модуль | `bh.<name>` | `bh.medical` |
| Зона | стабильный snake_case | `left_forearm` |
| Травма | `<zone>-<6 digits>` | `left_thigh-000001` |
| Запрос лечения | строка от сервера/клиента | `mp-17-42` |
| Событие | `Domain.Event` | `Character.InjuryCreated` |

Идентификатор травмы уникален в пределах персонажа. При достижении лимита
зоны травмы объединяются, а не перезаписываются молча.

## 9. Владение данными

| Данные | Владелец | Кто может менять |
|---|---|---|
| `anatomy.zones[].injuries` | Anatomy | Anatomy.Model, Medical через публичные методы |
| `physiology` | Physiology | Physiology |
| `medical.processedRequests` | Medical | Medical |
| `mind` | Mind (позже) | Mind |
| `metadata` | Persistence | Persistence, Core |

Medical не меняет внутренние поля Mind. Mind не меняет Anatomy напрямую.
Связь — через события и публичные методы.

## 10. Обработка ошибок

1. Ошибка модуля при инициализации:
   - модуль помечается `failed`;
   - зависимые помечаются `skipped`;
   - независимые продолжают работу;
   - событие `Core.ModuleFailed`.
2. Ошибка обработчика события:
   - `pcall`;
   - запись в журнал с именем события и id подписчика;
   - остальные подписчики продолжают.
3. Ошибка данных:
   - схема ремонтирует допустимые поля;
   - недопустимая запись карантинируется;
   - создаётся чистая запись;
   - критическая запись в журнал.
4. Ошибка лечения:
   - возвращается `{ ok=false, error=... }`;
   - состояние не меняется;
   - запрос не помечается выполненным.

## 11. Интеграция с базовой игрой

### 11.1. Базовое здоровье

`BodyDamage` остаётся авторитетным. BH не создаёт вторую шкалу здоровья и не
понижает `BodyPart:getHealth()`.

### 11.2. Наблюдение

`PlayerObserver`:

- хранит baseline 17 частей;
- сравнивает булевы состояния;
- создаёт запись только на переходе `false → true`;
- зеркалит базовую повязку;
- не создаёт травму на каждое событие `BLEEDING`.

### 11.3. Почему не перехват функций

Перехват `BodyDamage`/`IsoPlayer` без необходимости запрещён. Используются
события и публичные методы. Это снижает риск конфликтов с другими модами.

## 12. Сетевая граница

В v0.1 сетевой слой не реализован. Архитектурное правило на будущее:

- клиент отправляет **намерение** (`injuryId`, `actionId`, `requestId`);
- сервер проверяет расстояние, предметы, состояние, права и идемпотентность;
- сервер применяет эффект и отправляет результат;
- клиент не присылает severity, зону или готовый результат.

Подробнее: `docs/NETWORKING.md`.

## 13. Производительность

- наблюдение — раз в 30 кадров;
- 17 зон на игрока;
- не более 64 травм на персонажа;
- не более 8 на зону;
- нет полного обхода мира;
- нет тяжёлых расчётов в UI;
- удалённые сущности — упрощённая модель.

## 14. Ограничения v0.1

- нет полноценного UI;
- нет timed actions и анимаций лечения;
- нет серверной авторизации лечения;
- нет NPC, экономики, транспорта;
- нет сенсорной модели зомби;
- спина не является отдельной зоной;
- точность диагностики ограничена.

## 15. Решения, которые нельзя менять без миграции

1. Идентификаторы зон.
2. Формат `Injury`.
3. `schemaVersion` и семантика миграций.
4. Имена базовых событий.
5. Ключ `player:getModData().BH`.

Любое изменение этих пунктов требует новой версии схемы и теста миграции.
