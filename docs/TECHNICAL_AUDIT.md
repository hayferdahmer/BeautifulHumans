# Технический аудит Beautiful Humans

**Версия аудита:** 1.0  
**Дата:** 2026-10-25  
**Целевая игра:** Project Zomboid, Build 42  
**Зафиксированная сборка:** **42.21.0**, revision `4a0e9546ec`  
**Платформа:** Windows, Steam public branch, buildid `25485521`  
**Статус:** Stage 0 завершён; runtime-загрузка минимального мода подтверждена на выделенном сервере.

---

## 0. Краткое резюме

Аудит подтвердил, что базовая архитектура Beautiful Humans может опираться на
реальные механизмы Build 42:

- загрузка независимых модов и версионированных каталогов `42/` и `common/`;
- регистрация Lua-событий (`Events.OnGameStart`, `OnServerStarted`,
  `OnCreatePlayer`, `OnPlayerUpdate`, `OnPlayerGetDamage`, `OnHitZombie`);
- хранение пользовательских данных через `ModData` / `getModData()`;
- серверные и клиентские команды для авторитетной сетевой модели;
- 17 анатомических зон `BodyPartType`, совпадающих с телом персонажа;
- управление базовым состоянием зомби через `IsoZombie`;
- расширение предметов через `InventoryItem:getModData()` и состояние.

Одновременно зафиксированы существенные ограничения:

- в `OnPlayerGetDamage` **нет индекса анатомической зоны**; зону нужно выводить
  из состояния `BodyDamage` и/или `OnWeaponHitCharacter`;
- `OnPlayerGetDamage` для кровотечения может срабатывать **каждый кадр**;
- отдельной зоны «спина» в `BodyPartType` нет;
- полноценного публичного API для создания и управления человеческими NPC нет;
- у `IsoZombie` нет подтверждённого `setSpeedMod`; доступны `setCrawler`,
  `setWalkType`, `setTarget` и состояния базового AI;
- нельзя обещать полноценную физику разрушения зданий или произвольную
  анимационную систему без дополнительных ресурсов и проверок.

Эти ограничения не блокируют первый вертикальный срез, но меняют дизайн:
**базовая игра остаётся источником истины для здоровья, кровотечения и
заражения**, а Beautiful Humans хранит структурированные записи травм,
лечения и функциональных последствий.

## 4. Детальные результаты

### 4.1. Анатомия

**Подтверждённые факты**

- `BodyPartType` содержит 17 индексируемых частей: голова, шея, грудь,
  живот, пах, верхние/нижние части рук, кисти, бёдра, голени, стопы.
- `BodyDamage:getBodyPart(BodyPartType)` и `BodyDamage:getBodyParts()`
  доступны из Lua.
- У `BodyPart` есть состояние: `isBitten()`, `isCut()`, `isScratched()`,
  `isDeepWounded()`, `getFractureTime()`, `getBurnTime()`,
  `getBleedingTime()`, `bandaged()`, `getWoundInfectionLevel()`,
  `getHealth()`, `SetBandaged`/`setBleedingTime` и другие методы.
- Событие `OnPlayerGetDamage(character, damageType, damage)` подтверждено.
  Типы включают `BLEEDING`, `FALLDOWN`, `WEAPONHIT`, `CARHITDAMAGE`,
  `CARCRASHDAMAGE`, `INFECTION`, `SICK`, `HUNGRY`, `THIRST`.
- `OnHitZombie(zombie, wielder, bodyPart, weapon)` передаёт анатомическую
  часть зомби.
- `OnWeaponHitCharacter(attacker, target, weapon, damageSplit)` не передаёт
  часть тела.

**Ограничения**

1. В `OnPlayerGetDamage` нет body part. Надёжный способ — сравнивать
   состояние 17 частей до/после события и создавать травму на переходе
   `false → true`.
2. Для `BLEEDING` событие может срабатывать каждый кадр. Нельзя создавать
   травму на каждое событие; нужен debounce и baseline.
3. Отдельной зоны «спина» нет. В v0.1 спина не является самостоятельной
   зоной; при необходимости она будет метаданным травмы груди/живота.
4. Точная симуляция суставов, связок и костей невозможна. Модель использует
   функциональные группы с обоснованными штрафами.

**Решение для BH v0.1**

- 17 логических зон, взаимно однозначно отображённых на `BodyPartType`.
- `BodyDamage` — источник истины по здоровью, кровотечению и заражению.
- BH создаёт структурированную запись травмы только при переходе состояния;
  запись не заменяет базовое здоровье.
- `OnPlayerUpdate` опрашивает часть тела не каждый кадр, а раз в
  `tickInterval` (по умолчанию 30 кадров).

### 4.2. Зомби

**Подтверждённые факты**

- `IsoZombie` — управляемый класс с методами `setTarget`, `setCrawler`,
  `setCrawlerType`, `setWalkType`, `setState`, `setTargetSeenTime`,
  `isTargetVisible`, `isTargetLocationKnown`, `getTargetSeenTime`,
  `isTargetInCone`, `setLastHeardSound`.
- События `OnZombieUpdate`, `OnZombieDead`, `OnHitZombie` доступны.
- `ZombiePopulationManager` управляет реальными/виртуальными зомби и
  обновлением по расстоянию.

**Ограничения**

- `setSpeedMod` в публичных строках класса не обнаружен. Влияние на скорость
  следует выражать через `setWalkType`, `setCrawler`, состояния AI и
  временные модификаторы, а не через несуществующий сеттер.
- Замена всей AI-системы неоправданна: базовый state machine уже выполняет
  навигацию, атаку и восприятие. BH должен дополнять стимулы и функциональные
  ограничения, а не писать второй AI.
- Массовое обновление каждого зомби каждый тик запрещено. Нужен диспетчер с
  бюджетом и упрощённая модель для удалённых сущностей.

**Решение для BH**

- v0.1: пассивный мост `OnHitZombie`, без изменения AI.
- Следующий этап: функциональные состояния и `setCrawler`/`setWalkType` на
  основе структурных повреждений, с профилированием.

### 4.3. Зрение и слух

**Подтверждённые факты**

- `IsoZombie:isTargetVisible()`, `canSeeTarget()`, `isTargetLocationKnown()`,
  `getTargetSeenTime()`, `isTargetInCone()`.
- `IsoZombie:setLastHeardSound(...)`, `getBiggestSoundZomb()`.
- Событие `OnWorldSound` доступно.

**Ограничения**

- Нет публичного «сенсорного события» с полным набором параметров
  (громкость, направление, препятствия) для каждого зомби. Модель восприятия
  должна опрашивать состояние и дополнять его эвристиками.
- Точная проверка линии видимости и освещённости может быть дорогой; нужен
  бюджет и упрощение для удалённых зомби.

**Решение**

- Не заменять зрение/слух. Хранить последний стимул и «последнюю известную
  область», а не точные координаты игрока.
- Для v0.1 сенсорная модель не активна; она вынесена в BH Undead.

### 4.4. NPC

**Подтверждённые факты**

- В игре есть `IsoSurvivor`, `SurvivorDesc`, `SurvivorFactory`,
  `SurvivorGroup`, событие `OnCreateSurvivor`.
- Это подтверждает наличие инфраструктуры, но не публичного API для
  произвольного создания, выдачи задач и управления навигацией.

**Ограничения**

- Полноценные автономные NPC с профессиями, торговлей и патрулями в v0.1
  невозможны без отдельного исследовательского прототипа.
- Нельзя обещать «массовую симуляцию общества» до подтверждения
  производительности и стабильности.

**Решение**

- Stage 6 откладывается. В v0.1 нет обязательных NPC.
- Будущий прототип должен начинаться с одного охранника/торговца и
  документированной альтернативы, а не с «армии NPC».

### 4.5. Многопользовательский режим

**Подтверждённые факты**

- `sendClientCommand(player, module, command, args)`.
- `sendServerCommand(player, module, command, args)`.
- `Events.OnClientCommand(module, command, player, args)`.
- `Events.OnServerCommand(module, command, args)`.
- `ModData` и `getModData()` реплицируются движком; для точечной
  синхронизации частей тела используется `syncBodyPart`.

**Ограничения**

- Клиентский Lua не является доверенной стороной. Любое критическое действие
  должно повторно проверяться на сервере.
- `modData` — не транзакционная БД. Нужны идемпотентные request id,
  проверка расстояния, наличия предметов и прав.
- BH Networking в v0.1 ещё не реализован; текущий срез проверен на сервере
  без клиента.

**Решение**

- Server-authoritative модель, описанная в `docs/NETWORKING.md`.
- В v0.1 лечение через консоль/отладку не считается сетевым API.

### 4.6. Сохранения

**Подтверждённые факты**

- `player:getModData()`, `item:getModData()`, `object:getModData()`.
- Глобальный `ModData.getOrCreate(key)`.
- `OnPostSave`, `OnSave`, `OnLoad` доступны.
- Данные `modData` входят в сохранение игры; отдельный файл писать не нужно.

**Ограничения**

- Нет встроенной версионной схемы и миграций — BH реализует их сам.
- Объём `modData` влияет на размер сохранения. Нужны лимиты и удаление
  вылеченных записей.
- Прямой файловый ввод-вывод из игрового Lua не используется.

**Решение**

- Схема `schemaVersion=1`, миграции, ремонт, карантин повреждённых записей.
- Лимиты: 64 травмы на персонажа, 8 на зону, 32 обработанных запроса.

### 4.7. Предметы

**Подтверждённые факты**

- `InventoryItem:getModData()`, `setModData()`, `getCondition()`,
  `setCondition()`.
- Статические определения предметов находятся в скриптах, а не в Lua.
- `ItemContainer` предоставляет `getFirstType`, `getFirstTag`, `Remove`,
  `contains` и рекурсивные варианты.

**Ограничения**

- Нельзя добавлять произвольные поля в класс предмета; только `modData`.
- Динамические свойства нужно хранить компактно, иначе сохранения растут.

**Решение**

- Разделение «определение предмета» / «состояние экземпляра».
- В v0.1 BH не изменяет предметы; это Stage 4.

### 4.8. Транспорт

**Подтверждённые факты**

- Классы `BaseVehicle`, `VehiclePart`, события `OnEnterVehicle`,
  `OnMechanicActionDone`, `OnVehicleDamageTexture`.
- У частей транспорта есть состояние и `modData`.

**Ограничения**

- Детальный аудит ремонта, компонентов и синхронизации ещё не выполнен.
- Полноценная физика транспорта не является целью BH.

**Решение**

- Stage 7, после стабилизации Core/Medical/Engineering.

### 4.9. Анимации

**Подтверждённые факты**

- Анимации описываются XML/AnimSet; доступны `setVariable`,
  `setActionAnim`, `playAnim`.
- Можно использовать существующие анимации для новых действий.

**Ограничения**

- Нельзя обещать новую полноценную анимационную систему без ресурсов,
  скелета и проверки пайплайна.
- В v0.1 анимации не добавляются.

### 4.10. Строительство

**Подтверждённые факты**

- `IsoThumpable`, `OnDestroyIsoThumpable`, `OnDoTileBuilding`.
- У объектов есть `modData` и состояние.

**Ограничения**

- Полная разрушаемость каждого здания и физика материалов не подтверждены.
- Нужны ограниченные состояния повреждения с понятными последствиями.

**Решение**

- Stage 4/5, ограниченные состояния; не обещать физику каждого материала.

## 5. Что упрощается или откладывается

### Упрощается в v0.1

| Функция | Решение |
|---|---|
| Анатомия | 17 функциональных зон вместо суставов/связок |
| Диагностика | точная тяжесть скрыта до `examine` |
| Лечение | доменные действия + отладочный вызов; без полного timed action UI |
| Зомби | пассивный мост, без нового AI |
| Сеть | только фундамент; критическое лечение пока не является сетевым API |
| Предметы | без изменений в v0.1 |
| Анимации | без новых ассетов |

### Откладывается

- полноценные NPC и профессии;
- экономика, торговля, жильё;
- фракции и военные операции;
- массовая симуляция животных;
- разрушаемость зданий;
- персонализация снаряжения;
- полноценный UI всех систем.

## 6. План тестирования производительности

### 6.1. Стенд

Зафиксировать:

- CPU, GPU, RAM, SSD/HDD;
- разрешение и настройки графики;
- версию игры и buildid;
- список модов;
- число зомби, NPC, предметов;
- длительность прогрева.

Без фиксации стенда сравнение FPS бессмысленно.

### 6.2. Сценарии

1. Малый лагерь: 0–50 зомби, 1 игрок.
2. Массовое скопление: 300–800 зомби.
3. Несколько NPC (после Stage 6).
4. 500+ предметов с `modData`.
5. 4–8 игроков в мультиплеере.
6. Массовое обновление состояния (`Tick` 1000 травм).

### 6.3. Бюджеты

- `OnPlayerUpdate` observation: не более 1 прохода по 17 зонам раз в 30 кадров.
- `Anatomy.Tick`: не более 64 травм на персонажа.
- Запрещены полные обходы мира каждый тик.
- Для удалённых зомби — упрощённая модель, обновление реже.

### 6.4. Метрики

- время `OnPlayerUpdate`;
- время `Anatomy.Tick`;
- число активных сущностей;
- размер `modData` (байты);
- ошибки/предупреждения Lua;
- FPS p1/p5/median.

## 7. Журнал воспроизводимых проверок

### 7.1. Unit-тесты

Команда:

```powershell
node tools/run_tests.mjs
```

Результат:

```text
TEST_SUMMARY total=39 passed=39 failed=0 assertions=128
```

### 7.2. Runtime-тест

Мод `BHTestMod` загружен на выделенном сервере с `-cachedir` и целевой
сборкой 42.21.0. Ожидаемая строка:

```text
BH_TEST_RESULT PASS total=11 failures=0 version=0.1.0
```

Фактический результат совпал.

### 7.3. Что ещё не проверено

- одиночная игра с живым персонажем;
- фактическое сохранение/загрузка персонажа (не только имитация reload);
- повреждение от зомби и последующее лечение в игровом сценарии;
- мультиплеерный клиент и серверная проверка лечения;
- производительность при 300+ зомби;
- совместимость с популярными модами.

Эти пункты должны быть закрыты до релиза 1.0.0.

## 9. Вывод

Архитектура Beautiful Humans может быть построена на подтверждённых
механизмах Build 42. Критический риск — не загрузка мода, а корректное
сопоставление травм с зонами и сетевая авторитетность лечения. Поэтому
v0.1 сознательно ограничен:

- Core, Persistence, Anatomy, Physiology, Medical;
- один вертикальный срез;
- отсутствие NPC, экономики и массовой симуляции.

Это соответствует требованию ТЗ: сначала надёжный фундамент, затем
расширение.
