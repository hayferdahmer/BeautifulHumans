# Структура проекта Beautiful Humans

**Статус:** целевая структура. Вводится постепенно; не требует создания пустых каталогов заранее.

## 1. Принципы организации

1. Каталог отражает ответственность, а не этап разработки или имя автора.
2. Доменная логика отделена от Project Zomboid API, UI и сетевых протоколов.
3. Shared-код содержит чистые модели и правила, доступные обеим сторонам, но не доверяет клиенту.
4. Client-код отвечает за представление и пользовательский ввод.
5. Server-код отвечает за авторизацию, фиксацию изменений и фоновые процессы.
6. Каждый модуль имеет явный идентификатор bh.<domain> и список зависимостей.
7. Не создаём каталоги и файлы «на будущее», пока у них нет конкретного владельца и задачи.

## 3. Владение слоями

| Слой | Может | Не должен |
|---|---|---|
| Domain / shared | Хранить модели, вычислять правила, эмитить доменные события | Вызывать UI, читать клиентские команды напрямую |
| Integration/PZ | Читать игровые объекты и переводить API-события в доменные входы | Содержать полную медицинскую или экономическую логику |
| Networking | Валидировать запросы, маршрутизировать команды, синхронизировать ревизии | Принимать присланные клиентом результаты как истину |
| Client | Отображать состояние, отправлять намерения, управлять локальным UI | Самостоятельно фиксировать критические изменения |
| Server | Проверять полномочия, применять команды, сохранять и рассылать подтверждённые состояния | Дублировать доменные формулы в обработчиках сетевых событий |
| Persistence | Версионировать, проверять, мигрировать и восстанавливать данные | Становиться местом хранения несвязанных игровых правил |

## 4. Именование

- Файлы: PascalCase.lua для модулей и доменных моделей.
- Папки: PascalCase для доменов и подсистем.
- Идентификатор модуля: bh.<domain>; вложенные сервисы не обязаны становиться отдельными модулями реестра.
- События: Domain.SubjectChanged, Character.InjuryCreated.
- Сетевые команды: ограниченный namespace BH и явные имена команд.
- Идентификаторы сущностей должны быть стабильными и не зависеть от адресов Lua-таблиц.

## 5. Правило миграции текущего кода

Текущие файлы Anatomy, Physiology, Medical, Persistence и Integration остаются на своих местах. Новая структура создаётся постепенно, когда появляется реальная функциональность. Перемещение существующих файлов допускается отдельным PR с проверкой путей require, сборки и всех тестов.

## 6. Обязательные файлы будущего модуля

Для каждой крупной системы по мере её появления:

- Model.lua — структура состояния;
- Rules.lua или профильные файлы правил — чистые расчёты;
- Service.lua — операции над моделью, если они нужны;
- Integration/ — только если системе нужен мост к API игры;
- tests/unit/ — проверки правил и инвариантов;
- docs/systems/<SYSTEM>.md — спецификация системы.

Не требуется создавать все перечисленные файлы, если система пока не реализуется.
