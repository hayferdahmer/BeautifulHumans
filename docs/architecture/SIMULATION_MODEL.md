# Модель симуляции Beautiful Humans

**Статус:** архитектурная спецификация + headless-tested вертикальный срез runtime. Интеграция с настоящим PZ Build 42 ещё требует in-game acceptance.

## 1. Цель

Сохранить содержательную непрерывность мира без полного пересчёта всех процессов на каждом кадре. Каждая система описывает состояние, время последнего обновления, частоту или событие следующего обновления и уровень детализации.

## 2. Уровни детализации

| Уровень | Область | Модель |
|---|---|---|
| L0 Active | Игрок и сущности, непосредственно участвующие во взаимодействии | подробные расчёты и быстрые реакции |
| L1 Nearby | Сущности в локальной зоне интереса | индивидуальные состояния, более редкие расчёты |
| L2 Regional | Удалённые агенты, поселения, популяции и предприятия | пакетные/агрегированные расчёты с индивидуальными ключевыми параметрами |
| L3 Global | Климатические тенденции, рынки, миграции, войны и мировые события | событийная и стратегическая модель |

Уровень выбирается не только по расстоянию. Учитываются взаимодействие, угроза, наблюдение игроком, важность события и требования конкретной подсистемы.

## 3. Контракт процесса симуляции

Любой процесс должен определить:

- стабильный processId;
- владельца состояния;
- входные данные;
- выходные изменения;
- игровое время последнего обновления;
- минимальный/целевой интервал;
- приоритет;
- стоимость или лимит работы;
- поведение при пропуске нескольких интервалов;
- правила перехода между LOD;
- требования к серверной авторитетности;
- тесты детерминированности или допустимого диапазона результата.

Процесс получает elapsed game time и не должен предполагать, что между двумя вызовами прошёл ровно один кадр или один игровой тик.

## 4. Семантика времени

- Используется игровое время Project Zomboid, когда оно доступно.
- Вне игрового runtime чистые модели принимают время явно через аргументы.
- Время не берётся скрыто из глобального API внутри доменных формул.
- При паузе/остановке мира процессы не должны самопроизвольно ускоряться по реальному времени.
- При большом скачке времени система применяет bounded catch-up, агрегированную формулу или пакет событий; запрещены бесконечные циклы догоняющих тиков.
- Обработка длительного отсутствия игрока должна быть эквивалентна прохождению времени, насколько это допускает выбранная модель.

## 5. События и расписание

События используются для немедленных причинно-следственных изменений: травма, начало кровотечения, заражение, пожар, смерть, смена владельца, начало войны.

Плановые процессы используются для постепенных изменений: заживление, метаболизм, потребности NPC, рост растений, популяционная динамика, экономика и климат.

Событие не должно автоматически запускать полный обход мира. Оно изменяет затронутые сущности и планирует необходимые последующие процессы.

## 6. Переходы LOD

При переходе L0 → L2:
1. фиксируется точное состояние активной сущности;
2. сохраняется временная отметка;
3. вычисляется агрегированное представление;
4. удаляются только временные runtime-кэши, не доменное состояние.

При переходе L2 → L0:
1. определяется elapsed game time;
2. фоновая модель доводится до текущего времени;
3. восстанавливается индивидуальное состояние;
4. проверяются инварианты;
5. сущность подключается к активным процессам.

Переходы должны сохранять причинность и не создавать дублирующие эффекты.

## 7. Серверная модель

Сервер владеет каноническим состоянием и расписанием всех значимых процессов. Клиент может отображать предсказанную анимацию, рассчитывать локальные эффекты интерфейса, выполнять предварительные вычисления для последующей проверки сервером и кэшировать подтверждённые снимки.

Клиент не может самостоятельно подтверждать здоровье, травмы, предметы, деньги, навыки, право собственности, смерть NPC или мировые события.

## 8. Производительность

Каждый процесс должен иметь:
- ограничение числа сущностей за проход;
- лимит времени или операций;
- приоритет и возможность отложить необязательную работу;
- защиту от повторной регистрации;
- метрики времени выполнения и размера состояния.

Не допускаются:
- полный обход всех NPC/зомби/предметов каждый кадр;
- бесконечный catch-up;
- расчёты доменной логики внутри render;
- передача полного состояния мира каждый кадр;
- неограниченный рост журналов и modData.

## 9. Статус реализации

Реализованы Clock, ограниченный Scheduler, базовая политика LOD и вертикальный срез обработки онлайн-игроков. LOD пока не управляет реальными NPC/животными/регионами; региональная симуляция и полноценный сетевой authority framework не реализованы.
## 10. Реализованный фундамент (первый вертикальный срез)

В ветке `feat/simulation-architecture-foundation` добавлены:

- `Clock.lua`: инъецируемый источник времени, контроль конечности значений, защита от движения времени назад и расчёт elapsed time.
- `Scheduler.lua`: детерминированный порядок по приоритету и ID, уникальные process ID, интервалы, bounded execution budget, единичный запуск с накопленным elapsed time, изоляция ошибок callback, enable/disable/unregister.
- `LOD.lua`: чистая политика выбора L0–L3 по расстоянию и контекстным факторам важности.
- `Simulation.lua`: фасад создания clock/scheduler и регистрация модуля `bh.simulation`.
- `spec_simulation.lua`: headless-тесты для часов, scheduler и LOD.

**Подключение к серверу:** `ServerRuntime.lua` регистрирует запуск на `OnServerStarted`, затем вызывает Scheduler из серверного `OnTick`. Раз в одну игровую минуту процесс `bh.server.players` получает `getOnlinePlayers()` и передаёт каждого игрока в `Player.OnServerSimulationTick`. Общая функция `Player.ProcessSimulation` выполняет наблюдение базовых травм, прогрессирование травм и расчёт физиологии. Клиентский `OnPlayerUpdate` использует тот же процессор в локальном режиме.\n\n**Ограничения текущего среза:** runtime подключён, но его поведение ещё не подтверждено запуском на реальном dedicated server Build 42.21.0. LOD пока не управляет реальными NPC/животными/регионами; переходы LOD не сериализуют состояние; нет сетевого распределения расписания и полноценного server-authoritative протокола медицинских процедур.

## 11. Серверный runtime: границы и гарантии

- Серверный runtime запускается, если `isServer()` подтверждает серверный процесс; это покрывает dedicated и host/listen-server при условии подтверждения API в целевой версии игры.
- В качестве источника времени используется `getGameTime():getWorldAgeHours()`; системные часы не управляют ходом симуляции.
- Серверный процесс запускается после `OnServerStarted`, а Scheduler вызывается из `OnTick`.
- Список игроков читается через `getOnlinePlayers()`. У каждого игрока отдельный накопитель долга времени: ошибка одного не откатывает уже успешно обработанных игроков.
- Игровое время переводится в минуты. На одного игрока за проход обрабатывается не более 60 минут; остаток сохраняется и догоняется последующими проходами. Ошибка сохраняет весь долг этого игрока. Это ограничивает стоимость одного прохода, не отбрасывая elapsed time.
- `Player.ProcessSimulation` — общий доменный путь. В одиночной игре локальный путь накапливает долг и обрабатывает до 60 минут за проход; в мультиплеере единственный владелец — сервер.
- Headless-тесты проверяют адаптер коллекции игроков, bounded catch-up, per-player debt и изоляцию ошибок. Они не заменяют проверку Java-backed API в самой игре.
