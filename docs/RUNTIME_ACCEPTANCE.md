# Приёмка runtime Beautiful Humans в Project Zomboid

**Цель:** подтвердить поведение интеграции и симуляционного runtime в реальной игре.  
**Целевая среда:** Project Zomboid Build 42.21.0, revision 4a0e9546ec, Steam buildid 25485521.  
**Статус:** сценарии подготовлены; запуск после последних изменений ещё не подтверждён.

## 1. Что именно проверяем

Проверка разделена на независимые критерии:

1. **Загрузка:** игра нашла оба мода и Lua-файлы выполнились.
2. **Инициализация:** модули BH перешли в ready, runtime service загружен.
3. **Владение симуляцией:** только ожидаемая сторона запускает канонический runtime.
4. **Игровой цикл:** персонаж действительно проходит обработку, а ошибки не появляются в Lua-логе.
5. **Сохранение:** состояние переживает сохранение и повторную загрузку.
6. **Сеть:** сервер и клиенты не создают конкурирующие версии состояния.

Успешная строка BH_TEST_RESULT PASS сама по себе не доказывает корректность всех шести критериев.

## 2. Подготовка стенда

1. Собрать свежие артефакты из текущего PR: node tools/build.mjs.
2. Скопировать releases/BeautifulHumansCore и releases/BHTestMod в пользовательский каталог Zomboid/mods.
3. Включить оба мода. BHTestMod зависит от BeautifulHumansCore.
4. Для серверных прогонов использовать отдельный -cachedir, чтобы не смешивать логи и сохранения с рабочим сервером.
5. Перед каждым сценарием очистить или переименовать предыдущий console.txt / server log.
6. Зафиксировать версию игры, список модов, режим, число игроков и SHA собранного исходника.

Не запускать одновременно старую копию мода из Workshop и тестовую локальную копию.

## 3. Сценарий A — одиночная игра

**Стенд:** один игрок, локальный мир, оба мода включены.

1. Запустить новую или тестовую игру.
2. Дождаться загрузки мира и выполнения BHTestMod.
3. Найти в console.txt строки:
   - BH_RUNTIME_ACCEPTANCE mode=single-player;
   - BH_TEST_RESULT PASS.
4. Убедиться, что в диагностике runtimeStarted=false: одиночная игра не должна поднимать серверный scheduler.
5. Создать персонажу тестовую травму через debug-консоль:
   BH.Commands.Injury("left_thigh", "cut", 60).
6. Проверить BH.Commands.Self(), затем применить тестовое лечение:
   BH.Commands.Treat(nil, "bandage").
7. Убедиться, что кровотечение остановлено и запись травмы не дублируется.
8. Сохранить игру, полностью выйти в меню, загрузить тот же мир.
9. Повторить BH.Commands.Self(): травма и состояние лечения должны сохраниться ровно один раз.

**Pass:** локальный путь доступен; серверный runtime не запущен; лечение и сохранение согласованы; нет Lua exceptions.

**Fail:** mode=unknown, модуль не готов, server runtime стартовал в одиночной игре, состояние пропало/дублировалось или есть необработанная ошибка.

## 4. Сценарий B — dedicated server, один клиент

**Стенд:** отдельный dedicated server и один подключённый клиент.

1. Запустить сервер с отдельным cachedir и Mods=BeautifulHumansCore;BHTestMod.
2. В серверном логе найти:
   - BH_RUNTIME_ACCEPTANCE mode=multiplayer-server;
   - BH_TEST_RESULT PASS;
   - Server-authoritative simulation runtime started.
3. Убедиться, что серверная диагностика сообщает runtimeStarted=true.
4. Подключить клиента.
5. В клиентском console.txt найти:
   - BH_RUNTIME_ACCEPTANCE mode=multiplayer-client;
   - BH_TEST_RESULT PASS.
6. Убедиться, что на клиенте runtimeStarted=false, а строка запуска server-authoritative runtime отсутствует.
7. Создать/получить тестовую травму на персонаже и проверить её на сервере и клиенте.
8. Выполнить лечение допустимым игровым способом, сохранить сервер, перезапустить и переподключиться.
9. Сверить, что состояние не дублируется и клиент не перезаписывает серверное.

**Pass:** runtime запущен только на dedicated server; клиент сообщает, что не является владельцем; нет двойной обработки.

**Fail:** runtime запущен на клиенте, не запущен на сервере, сервер и клиент показывают разные подтверждённые состояния или есть Lua exceptions.

## 5. Сценарий C — host/listen-server + два клиента

**Стенд:** один игрок создаёт host, два других подключаются.

1. Запустить host и дождаться загрузки мира.
2. В логе host найти mode=multiplayer-server и runtimeStarted=true.
3. Подключить два клиента.
4. В логах обоих клиентов найти mode=multiplayer-client и runtimeStarted=false.
5. Убедиться, что host не запускает локальный путь через OnPlayerUpdate: при isMultiplayer()==true он должен возвращаться из локального observer.
6. На каждом клиенте выполнить одинаковый безопасный тестовый сценарий с разными персонажами.
7. Проверить серверный лог: на одного игрока приходится один проход обработки за плановый интервал; нет повторных записей травм.
8. Отключить одного клиента, продолжить игру, подключить его снова.
9. Сохранить мир, остановить host, снова запустить и проверить состояние всех трёх персонажей.

**Pass:** host — единственный владелец серверного runtime; оба удалённых клиента не запускают его; переподключение не создаёт дублей; сохранения сохраняют состояние.

**Fail:** host одновременно обрабатывает игрока серверным и локальным путём, клиент запускает scheduler, состояние расходится или дублируется.

## 6. Сбор диагностических результатов

Для каждого режима сохранить:

- полный лог запуска;
- строки BH_RUNTIME_ACCEPTANCE;
- строку BH_TEST_RESULT;
- строки запуска/ошибки runtime;
- скриншот или текст результата BH.Commands.Self();
- результат сохранения и повторной загрузки;
- число подключённых игроков и точное время проверки.

PowerShell для первичного фильтра лога:

~~~powershell
Select-String -Path "$env:USERPROFILE\Zomboid\console.txt" -Pattern "BH_RUNTIME_ACCEPTANCE|BH_TEST_RESULT|Server-authoritative simulation|\[BH\].*ERROR|Exception"
~~~

Для dedicated server укажи фактический путь к его console.txt или лог-файлу вместо пользовательского пути выше.

## 7. Матрица приёмки

| Проверка | Single-player | Dedicated | Host + 2 clients |
|---|---|---|---|
| BHTestMod загружен | обязательно | обязательно | обязательно |
| Runtime mode определён | single-player | multiplayer-server | host server + clients |
| ServerRuntime started | нет | да, только сервер | да, только host |
| Клиентский canonical tick | неприменимо | нет | нет |
| Живой персонаж обработан | да | да | все три |
| Save/load | да | да | да |
| Reconnect | неприменимо | да | да |
| Lua errors | 0 | 0 | 0 |

## 8. Ограничения тестового модуля

BHTestMod печатает режим и проверяет базовое владение runtime. Это диагностический smoke test, не полноценный античит и не доказательство корректности всех сетевых процедур.

Отдельно остаются:
- server-side start/complete reservation protocol для медицинских timed actions;
- авторизация команд лечения, проверка предметов, дистанции и request ID;
- устойчивое сохранение catch-up debt между перезапусками сервера;
- политика offline progression;
- нагрузочный тест 16–32 игроков и измерение server tick.

## 9. Решение по результатам

- Любой Fail блокирует merge PR №4.
- Если все три режима проходят, приложить логи и SHA к PR и выполнить повторный аудит.
- Не считать отсутствие ошибок в логе достаточным, если не проверены лечение, сохранение и отсутствие двойного владельца.
- Не менять целевую версию игры без повторного аудита API.
