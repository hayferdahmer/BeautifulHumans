# Производительность Beautiful Humans

**Версия:** 0.1.0  
**Статус:** бюджеты Stage 1; профилирование в игровых сценах ещё впереди.

---

## 1. Принципы

1. Не обновлять всё каждый кадр.
2. Не сканировать мир без необходимости.
3. Кэшировать неизменяемые данные.
4. Ограничивать историю и количество сущностей.
5. Упрощать удалённые объекты.
6. Измерять, а не оценивать «на глаз».

---

## 2. Текущие бюджеты

| Операция | Частота | Стоимость |
|---|---|---|
| `Player.OnUpdate` | раз в 30 кадров (по умолчанию) | 17 зон + до 64 травм |
| `Anatomy.Tick` | раз в 30 кадров | до 64 травм |
| `Physiology.Tick` | раз в 30 кадров | O(травм) |
| `Medical.Apply` | по действию | O(1) + проверка предметов |
| `Persistence.GetCharacterData` | кэш | O(1) при повторном вызове |

`tickInterval` настраивается в `BH.Config` (1..600).

---

## 3. Ограничения данных

- 64 травмы на персонажа;
- 8 травм на зону;
- 32 обработанных запроса;
- 250 записей журнала в памяти;
- нет истории травм в v0.1.

Это защищает от неограниченного роста `modData`.

---

## 4. Что запрещено

- `OnTick` с полным обходом всех зомби;
- отдельный тяжёлый обработчик на каждого зомби;
- `getCell():getZombieList()` каждый кадр;
- полный обход инвентарей каждый кадр;
- расчёты UI в `render`;
- бесконечные цепочки событий;
- повторная регистрация обработчиков при каждом `OnGameStart`.

---

## 5. План профилирования

### 5.1. Стенд

Зафиксировать:

- CPU/GPU/RAM;
- ОС;
- настройки графики;
- версию игры;
- список модов;
- число зомби/NPC/предметов;
- длительность прогрева.

### 5.2. Сцены

| Сцена | Условия | Что измерять |
|---|---|---|
| S1 | 1 игрок, 0–50 зомби | baseline FPS, Lua time |
| S2 | 1 игрок, 300–800 зомби | FPS p1/p5, `OnZombieUpdate` |
| S3 | 4 игрока, база | server tick, modData size |
| S4 | 500 предметов с modData | размер сохранения, load time |
| S5 | 64 травмы, 1000 Tick | время `Anatomy.Tick` |
| S6 | 8 игроков, лечение | сетевые задержки, дубликаты |

### 5.3. Метрики

- среднее/пиковое время `OnPlayerUpdate`;
- время `Anatomy.Tick`;
- число активных сущностей;
- размер `player:getModData().BH` в байтах;
- FPS p1/p5/median;
- ошибки Lua;
- потребление RAM.

### 5.4. Критерии

Универсальные FPS-нормы не задаются. Вместо этого:

- эталонный стенд;
- бюджеты по времени;
- отсутствие деградации более чем на 10% относительно baseline
  при равном числе сущностей;
- отсутствие утечек `modData`.

## 6. Текущие измерения

Проведены только:

- unit-тесты (39 тестов, 128 assertions);
- runtime self-test на сервере (7 модулей, 0 ошибок).

Игровые FPS-замеры **не проводились**. Их нельзя подменять временем
headless-тестов.

---

## 7. Известные риски

1. `PlayerObserver` опрашивает 17 частей; при большом числе игроков это
   может стать заметным.
2. `Model.GetMobility` пересчитывает все зоны; при частых вызовах нужен кэш.
3. `modData` может расти при длинной игре; нужен аудит размера.
4. Будущие NPC/зомби-модули могут нарушить бюджеты без профилирования.

---

## 8. Правило для новых модулей

Новый модуль не принимается, если:

- он добавляет работу каждый кадр без бюджета;
- он сканирует мир;
- он не имеет упрощённой модели для удалённых объектов;
- он не измерен хотя бы в одной сцене;
- он увеличивает `modData` без лимита.
