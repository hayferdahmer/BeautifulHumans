# Сетевая модель Beautiful Humans

**Статус v0.1:** фундамент описан, серверная авторизация лечения ещё не
реализована.  
**Целевая модель:** server-authoritative.

---

## 1. Принципы

1. Клиент присылает **намерение**, а не результат.
2. Сервер проверяет существование, расстояние, предметы, права и состояние.
3. Сервер применяет эффект и рассылает подтверждённое состояние.
4. Клиент не может прислать `severity`, `zone`, `bandage=true` или готовый
   `Injury`.
5. Повторный запрос не должен повторно списывать предметы и начислять эффект.
6. Ошибка проверки не меняет состояние.

---

## 2. Подтверждённые API

```lua
-- client -> server
sendClientCommand(player, "BH", "treat", {
    injuryId = "left_thigh-000001",
    action = "bandage",
    requestId = "mp-17-42",
})

-- server -> client
sendServerCommand(player, "BH", "treatmentResult", {
    requestId = "mp-17-42",
    ok = true,
    injuryId = "left_thigh-000001",
    state = { ... },
})
```

Сервер:

```lua
Events.OnClientCommand.Add(function(module, command, player, args)
    if module ~= "BH" then return end
    -- validate and apply
end)
```

Клиент:

```lua
Events.OnServerCommand.Add(function(module, command, args)
    if module ~= "BH" then return end
    -- update cache/UI only
end)
```

---

## 3. Поток лечения

```text
Клиент
  │  treat(injuryId, action, requestId)
  ▼
Сервер
  ├─ 1. Модуль/команда существуют?
  ├─ 2. Игрок существует и жив?
  ├─ 3. Injury принадлежит этому игроку?
  ├─ 4. Действие допустимо для типа травмы?
  ├─ 5. Предметы есть в инвентаре?
  ├─ 6. requestId уже обработан?
  ├─ 7. Применить эффект
  ├─ 8. Списать предметы один раз
  ├─ 9. Сохранить/транслировать состояние
  └─ 10. treatmentResult(ok/error, state)
  ▼
Клиент
  └─ обновляет отображение, не меняет модель сам
```

---

## 4. Проверки

| Проверка | Обязательна | Примечание |
|---|---|---|
| Существование игрока | да | `player ~= nil` |
| Живость | да | мёртвый не лечится |
| Владение травмой | да | `injuryId` принадлежит character data игрока |
| Допустимость действия | да | `Medical.CanApply` |
| Наличие предмета | да | серверный инвентарь |
| Расстояние | да, если действие над другим игроком | для себя — не требуется |
| `requestId` | да | идемпотентность |
| Роль/права | для админ-действий | `getAccessLevel()` |
| Состояние мира | если применимо | дверь, контейнер, транспорт |

---

## 5. Идемпотентность

```lua
medical.processedRequests[requestId] = true
```

- хранится не более 32 записей;
- старые удаляются;
- повторный запрос возвращает `{ ok=false, duplicate=true }`;
- предметы не списываются повторно;
- событие `Character.TreatmentApplied` не эмитится повторно.

`requestId` должен быть уникальным на игрока/сессию. Клиентский UUID или
`onlineId + sequence` подходят.

---

## 6. Синхронизация состояния

### 6.1. Что отправлять

Минимальный снимок:

```lua
{
    injuryId = "...",
    zone = "left_thigh",
    kind = "cut",
    severity = 42.5,
    bleeding = 0,
    bandaged = true,
    splinted = false,
    status = "healing",
    revision = 17,
}
```

### 6.2. Что не отправлять

- полную историю;
- все зоны;
- ссылки на объекты;
- производные кэши;
- чужие травмы.

### 6.3. Ревизии

Каждая запись может иметь `revision` (монотонный счётчик). Клиент применяет
только более новую ревизию; устаревшие ответы игнорируются.

---

## 7. Защита от злоупотреблений

- не доверять `args` любого типа;
- проверять `type(args) == "table"`;
- ограничивать длину строк;
- не принимать `severity`, `zone`, `bleeding` от клиента;
- проверять `injuryId` по данным игрока, а не по глобальной таблице;
- проверять предметы на сервере;
- не позволять лечить чужого игрока без расстояния/разрешения;
- логировать отклонённые запросы с `player`, `module`, `command`;
- не раскрывать точные координаты в ответе.

---

## 8. Переподключение и устаревшие данные

1. При входе клиент запрашивает снимок состояния.
2. Сервер отправляет ревизию.
3. Если клиент имеет кэш с большей ревизией — он ждёт сервер.
4. После перезапуска сервера ревизия продолжается из сохранения.
5. `requestId` из прошлой сессии не считается доверенным, если он не в
   сохранённом списке; сервер решает по своим данным.

---

## 9. Тестовые сценарии

1. Клиент отправляет корректный `treat` — эффект один.
2. Тот же `requestId` повторно — `duplicate=true`, без списания.
3. Клиент присылает `severity=999` — поле игнорируется.
4. Клиент лечит чужую травму — отказ.
5. Клиент без бинта — отказ.
6. Клиент на другом конце карты лечит другого — отказ.
7. Разрыв соединения после применения — повторный запрос не дублирует.
8. Перезапуск сервера — состояние и ревизия сохраняются.
9. Устаревший ответ не откатывает более новое состояние.
10. Мод без сетевого модуля не ломает одиночную игру.

---

## 10. Текущий статус

| Элемент | Статус |
|---|---|
| `sendClientCommand` / `sendServerCommand` | подтверждены |
| `OnClientCommand` / `OnServerCommand` | подтверждены |
| Server-side `Medical.Apply` | есть доменный API |
| BH-команды `treat` | не реализованы |
| Инвентарная проверка на сервере | не реализована |
| Ревизии/снимки | не реализованы |
| MP-тесты | не реализованы |

До реализации сетевого слоя лечение через консоль/отладку **не является**
сетевым API и не должно использоваться в мультиплеере.
